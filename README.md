# QEMU BCM21553 — Samsung Galaxy Y GT-S5360 (totoro)

Экспериментальный форк QEMU для Samsung Galaxy Y на Broadcom BCM21553.
Основной сценарий — запуск **неизменённого стокового SBL**, чтение разделов
OneNAND, штатный логотип из `param.lfs` и переход к ядру из Android Boot Image.
Прошивки Samsung в репозиторий не входят. Полный запуск Android пока не подтверждён.

## Что работает

| Сценарий | Состояние |
| --- | --- |
| Прямой старт стокового SBL | Проверен с двумя версиями, файл и инструкции SBL не патчатся |
| Чтение `boot` и переход в стоковое ядро | Проверен вход в Linux, включая PC `0xc01e47c0` |
| Логотип Samsung GALAXY Y | SBL читает `logo.jpg` из `param.lfs`, декодирует и рисует через LCDC |
| Консоль SBL | Проверена команда `help`; вход после инициализации через отладчик |
| Свои C/ASM-ядра | Четыре цветных квадрата; Hello World и чтение регистров CPU |
| Работа своих ядер на телефоне | Автор эксперимента подтвердил запуск на настоящем GT-S5360 |
| Полный Android userspace | Не подтверждён |
| Полная точность NAND, ECC, модема, Wi-Fi | Не реализована / экспериментальна |

Выполнение начинается непосредственно с SBL по адресу `0x96800000`.
Mask ROM и предшествующие стадии загрузки не воспроизводятся.
В обычном запуске SBL сам читает ядро из флеша; `-kernel` не используется.
Версия базового дерева по `VERSION`: `11.1.50`; это не обещание совместимости
изменений с другими выпусками QEMU.
Исторические результаты: [docs/totoro-stock-sbl.md](docs/totoro-stock-sbl.md).

## Сборка

Команды выполняются из корня `qemu-bcm21553`, на Linux.
Для эмулятора нужен обычный C/C++ компилятор хоста. ARM cross-compiler нужен
только при отдельной сборке своего гостевого ядра.
Нужны Python 3, Ninja, pkg-config, GLib, Pixman, zlib; для окна — GTK 3.
`configure` проверяет версии и зависимости. Первоначальная настройка может
запрашивать зависимости Meson/Python и доступ к сети.

Пример пакетов Debian/Ubuntu; названия зависят от выпуска:

```sh
sudo apt install build-essential ninja-build python3 python3-venv \
    python3-pip meson pkg-config libglib2.0-dev libpixman-1-dev \
    zlib1g-dev libgtk-3-dev
```

Сборка только системного ARM-эмулятора:

```sh
mkdir -p build
cd build
../configure --target-list=arm-softmmu \
    --enable-gtk --disable-opengl --disable-docs --disable-werror --disable-rust
ninja qemu-system-arm
cd ..
./build/qemu-system-arm -machine help
```

В списке должна быть машина `totoro`. Обновление существующей сборки:

```sh
ninja -C build qemu-system-arm
```

На сервере без окна замените `--enable-gtk` на `--disable-gtk`.
Запуск с `-display gtk,gl=off` в такой сборке недоступен.
Утилиты подготовки проверяются на Linux и используют POSIX socketpair/pass_fds.
Наличие старой Windows-сборки не означает поддержку этих утилит в Windows.

## Подготовка флеша

### Входные файлы

Поддерживаемый сервисный пакет и рекомендуемое расположение:

```text
LegacySoC-Old/
├── qemu-bcm21553/
├── reference-firmware/
│   └── sbl.bin
└── S5360XXMK1_DBTML1_SVC/
    ├── BOOT_S5360XXMK1_REV05.tar.md5
    ├── MODEM_S5360XXMK1_REV05.tar.md5
    ├── PDA_S5360XXMK1_REV05.tar.md5
    ├── GT-S5360-csc-DBTML1.tar.md5
    └── totoro_0623.pit
```

Можно хранить файлы внутри игнорируемого `local/firmware/` и явно задавать пути.
Есть **две разные версии SBL**:

| Версия | SHA-256 | Использование |
| --- | --- | --- |
| Оригинальный `reference-firmware/sbl.bin` | `fdc8eecb28aa35d63c5286eeb645a3126ec2438d88e27fdd03b595fc8a6eb4d9` | Загрузка, подготовка, консоль |
| `Sbl.bin` из PDA S5360XXMK1 | `530420d82e8e1321a86b5b2ef93013c3b8f3f6ecdc6f55fcb39d1f6824c184b4` | Обычная загрузка готового флеша |

Подготовка и консоль используют адреса функций **первой** версии и проверяют SHA-256.
SBL из PDA не является заменой для этих операций. Если имеется только сервисный
пакет, запускать его SBL можно с готовым образом, но для подготовки с нуля этим
методом нужна также первая версия SBL.

### Создание нового образа

```sh
python3 scripts/prepare-totoro-flash.py \
    --firmware ../S5360XXMK1_DBTML1_SVC \
    --sbl ../reference-firmware/sbl.bin \
    --output local/flash
```

Каталог результата **не должен существовать**. Утилита не перезаписывает старый
образ. Для повторения укажите другой каталог, например `local/flash-new`.
Оставьте минимум 1 ГБ свободного места; сборка и исходная прошивка занимают
дополнительное место.

Порядок подготовки:

1. Проверяются версия SBL, поддерживаемая карта PIT, компоненты и их размеры.
2. Создаются `main.img` 512 MiB и `oob.img` 32 MiB со стёртым состоянием `0xff`.
3. Через GDB stub вызывается штатная `FSR_BML_Format`: SBL создаёт метаданные BML.
4. Копируются PIT и компоненты. `loke_bk` получает SBL, `boot_backup` — `boot.img`.
5. После нового запуска SBL вызываются `FSR_STL_Format`, `FSR_STL_Open`,
   `FSR_STL_Write` и закрытие J4FS для записи логического `param.lfs`.
6. Сохраняются карта, размеры и SHA-256 использованных компонентов в manifest.

Исходные SBL, PIT и архивы не меняются. Из TAR читаются только известные файлы;
произвольные пути и ссылки не извлекаются. SHA-256 в manifest фиксирует данные,
но не удостоверяет их происхождение. MD5-хвост `.tar.md5` отдельно не проверяется.

```text
local/flash/
├── main.img
├── oob.img
├── manifest.json
├── format-bml.log
└── format-param.log
```

Успех отмечен в manifest как `status: complete`. При ошибке остаётся
`status: incomplete` и логи. Такой каталог нельзя считать готовым флешем:
после диагностики повторите создание в новом каталоге.

```sh
python3 scripts/prepare-totoro-flash.py --help
```

`--qemu` задаёт бинарник, `--pit` — путь к PIT той же поддерживаемой раскладки.
Произвольные PIT и другие устройства этим не поддерживаются.

### Старый рабочий комплект

Лаунчеры поддерживают `build/sbl-stock/main.img` + `oob.img`, если нового
`local/flash/main.img` ещё нет. Не удаляйте старую папку вместе со сборкой,
пока не сохранили пару. Перенос при остановленном QEMU:

```sh
mkdir -p local/flash
cp build/sbl-stock/main.img build/sbl-stock/oob.img \
    build/sbl-stock/manifest.json local/flash/
```

**Main и OOB нужно сохранять вместе, только при остановленном эмуляторе.**
Несогласованная пара может не распознаваться BML/STL.

## Запуск SBL

С окном 240 × 320:

```sh
sh scripts/run-totoro-sbl.sh -display gtk,gl=off
```

Только UART:

```sh
sh scripts/run-totoro-sbl.sh
```

Выход: **Ctrl+A, затем X**. Переключение UART / QEMU monitor:
**Ctrl+A, затем C**. Это последовательные нажатия.
Рабочая пара по умолчанию открывается с разрешённой записью.
Запуск без изменения флеша:

```sh
TOTORO_ONENAND_RW=0 sh scripts/run-totoro-sbl.sh -display gtk,gl=off
```

Другая пара и SBL:

```sh
TOTORO_SBL="$PWD/local/firmware/Sbl.bin" \
TOTORO_FLASH_DIR="$PWD/local/flash-new" \
sh scripts/run-totoro-sbl.sh -display gtk,gl=off
```

По умолчанию SBL берётся из `../reference-firmware/sbl.bin`.
Пути с пробелами требуют кавычек; путь SBL с запятой отвергается из-за
синтаксиса `-device loader`.
Эквивалент базового запуска напрямую:

```sh
TOTORO_ONENAND_PROBE=1 \
TOTORO_ONENAND_IMAGE="$PWD/local/flash/main.img" \
TOTORO_ONENAND_OOB="$PWD/local/flash/oob.img" \
TOTORO_ONENAND_RW=0 \
./build/qemu-system-arm -M totoro -display gtk,gl=off -serial mon:stdio \
    -device loader,file=../reference-firmware/sbl.bin,addr=0x96800000,cpu-num=0,force-raw=on
```

Нужен бинарник этого форка: системный QEMU обычно не знает `totoro`.
Не запускайте одновременно два процесса с записью в одну пару флеша.

## Консоль SBL

```sh
python3 scripts/run-totoro-sbl-console.py
```

После `SBL>` можно вводить:

```text
help
printenv
showpart
```

Это штатный обработчик команд SBL, но вход организован через отладчик,
а не комбинацией кнопок телефона:

1. Остановка после инициализации по адресу `0x968116cc`.
2. Разрешение UART-логирования байтом RAM по `0x96a09a8c`.
3. Установка `r0 = 0x96000000` (буфер) и `PC = 0x96800494` (command_loop).
4. Отключение GDB; далее команды выполняет SBL.

Файл и инструкции SBL неизменны; состояние RAM и регистров для входа в
консоль меняется. Обычная холодная загрузка такого перенаправления не делает.
В консоли запись выключена по умолчанию; `TOTORO_ONENAND_RW=1` разрешает её.
Для изменяющих команд используйте отдельную копию пары.

Проверка консоли без интерактивного сеанса:

```sh
python3 scripts/run-totoro-sbl-console.py --check
```

Отправляется `help`, проверяется строка `Following commands are supported`,
затем QEMU завершается. Это проверяет консоль, а не загрузку Android.

## Память и разделы

### Геометрия OneNAND

| Параметр | Значение |
| --- | --- |
| Основные данные страницы | 4096 байт |
| Spare / OOB страницы | 256 байт |
| Страниц в блоке | 64 |
| Основные данные блока | 262144 байта = 256 KiB |
| Блоков | 2048 |
| main.img | 536870912 байт = 512 MiB |
| oob.img | 33554432 байта = 32 MiB |

Основные данные и OOB хранятся отдельно, не чередуются.
Для страницы `p`: смещение в main равно `p × 4096`, в OOB — `p × 256`.
Для блока `b`: смещение в main равно `b × 0x40000`.
Стёртая NAND заполнена `0xff`; нулевой файл после `truncate` ей не эквивалентен.

### Карта totoro_0623.pit

| Раздел | ID | Первый блок | Блоков | Размер, KiB | Содержимое |
| --- | ---: | ---: | ---: | ---: | --- |
| bcm_boot | 0 | 0 | 1 | 256 | BcmBoot.img |
| loke | 1 | 1 | 8 | 2048 | Sbl.bin из PDA |
| loke_bk | 2 | 9 | 8 | 2048 | Копия loke |
| systemdata | 3 | 17 | 1 | 256 | PIT |
| modem | 4 | 18 | 50 | 12800 | BcmCP.img |
| param_lfs | 21 | 68 | 20 | 5120 | param.lfs через STL |
| boot | 5 | 88 | 20 | 5120 | boot.img |
| boot_backup | 6 | 108 | 20 | 5120 | Копия boot.img |
| system | 20 | 128 | 920 | 235520 | system.img |
| cache | 22 | 1048 | 160 | 40960 | csc.rfs |
| userdata | 23 | 1208 | 789 | 201984 | userdata.img |
| efs | 7 | 1997 | 1 | 256 | Нет входного содержимого |
| sysparm_dep | 8 | 1998 | 1 | 256 | Нет в используемом пакете |
| umts_cal | 9 | 1999 | 1 | 256 | Нет в используемом пакете |
| cal | 10 | 2000 | 4 | 1024 | Нет входного содержимого |
| Резерв BML | — | 2004 | 44 | 11264 | Метаданные и резерв |

Это карта **сконструированного образа**, а не побайтового дампа телефона.
Вымышленные EFS, IMEI и калибровки не генерируются.
PIT состоит из заголовка 28 байт и записей по 132 байта: девять 32-битных
little-endian полей и три строки по 32 байта. В этой разновидности PIT
размер блока и число блоков не являются готовыми физическими смещениями.
Начала разделов получены последовательной раскладкой и согласованы с
созданной BML-таблицей и наблюдаемым выводом SBL.

### BML, STL, J4FS

```text
main.img + oob.img
      ↓
OneNAND — страницы, блоки, команды и регистры состояния
      ↓
BML — разделы, резерв, служебные метаданные
      ↓
STL — логические секторы param_lfs
      ↓
J4FS — файлы параметров и logo.jpg
      ↓
SBL → LCDC → экран QEMU
```

PIT описывает разбиение, но не создаёт служебную область BML.
BML управляет блоками NAND, STL предоставляет логические секторы,
J4FS позволяет находить файлы внутри `param.lfs`.
Поэтому простое `dd param.lfs` в начало физического раздела недостаточно:
подготовщик записывает его через штатные функции STL.
Для `system`, `cache`, `userdata` пока выполнено физическое размещение
компонентов; их полноценное монтирование не подтверждено.
Переход в ядро не доказывает загрузку Android.

## Логотип

SBL открывает J4FS, читает и декодирует `logo.jpg`. LCDC принимает DCS-команды
`0x2a` / `0x2b` (окно столбцов/строк), `0x2c` (пиксели GRAM).
SBL пишет пиксели программно; при включении DMA LCDC используется путь
framebuffer ядра. Размер изображения — 240 × 320.

Опция машины `boot-param` относится к отдельной подстановке изображения
со стороны хоста. В описанных командах её нет: логотип рисует сам SBL.
В исторической проверке breakpoint `0x96811774` фиксировал экран после
рисования; обычный лаунчер его не ставит. Логотип может быстро смениться
изображением ядра.
Ошибки создания `param.blk` / `switch_sel` не исключают успешного чтения
логотипа: полное поведение записываемой J4FS ещё не проверено.

## Собственное ядро

Проекты `four-squares/` и `hello-cpu/` находятся рядом с QEMU в рабочем дереве
автора и **не входят в этот репозиторий**. Их собственные README описывают
сборку. По сообщению автора, оба варианта работают на настоящем GT-S5360.
Это собственные C/ASM-программы, а не Linux; шрифт TTY не меняет этого.
Сведения CPU читаются из CP15; телефон и ARM-модель QEMU могут возвращать
разные поля идентификации.

Проверенные образы используют классический **Android Boot Image v0**:

| Поле | Значение |
| --- | --- |
| Magic | ANDROID! |
| Размер страницы контейнера | 4096 |
| Адрес ядра | 0x81608000 |
| Адрес ramdisk | 0x82600000 |
| Адрес second stage | 0x82500000 |
| Адрес tags | 0x81600100 |

Заголовок и компоненты выровнены по странице. `boot.img` читает SBL из
раздела; передавать этот контейнер как `qemu -kernel` здесь не нужно.

### Установка boot.img в копию флеша

Остановите QEMU. Пример создаёт **новую** пару `local/my-boot/` и заменяет
основной и резервный boot. Используется карта из таблицы выше.

```sh
python3 - /absolute/path/to/boot.img <<'PY'
from pathlib import Path
import shutil
import sys

boot = Path(sys.argv[1]).read_bytes()
block = 256 * 1024
size = 20 * block
if not boot.startswith(b'ANDROID!') or len(boot) > size:
    raise SystemExit('Expected Android boot.img fitting a 5 MiB partition')
source = Path('local/flash')
if (source / 'main.img').stat().st_size != 512 * 1024 * 1024:
    raise SystemExit('Unexpected main image geometry')
if (source / 'oob.img').stat().st_size != 32 * 1024 * 1024:
    raise SystemExit('Unexpected OOB geometry')
dest = Path('local/my-boot')
dest.mkdir()
for name in ('main.img', 'oob.img'):
    shutil.copyfile(source / name, dest / name)
with (dest / 'main.img').open('r+b') as image:
    for first_block in (88, 108):
        image.seek(first_block * block)
        image.write(boot + b'\xff' * (size - len(boot)))
print(dest.resolve())
PY

TOTORO_FLASH_DIR="$PWD/local/my-boot" \
sh scripts/run-totoro-sbl.sh -display gtk,gl=off
```

Magic/размер — минимальная проверка, не полная валидация заголовка.
Эта операция относится к образу эмулятора с данной раскладкой.
**Main/OOB не являются образами для прошивки телефона.** Для телефона
используется отдельно подготовленный `boot.img`, соответствующий устройству.

## Параметры

| Переменная | Назначение |
| --- | --- |
| QEMU_BINARY | Бинарник, по умолчанию build/qemu-system-arm |
| TOTORO_SBL | SBL, по умолчанию ../reference-firmware/sbl.bin |
| TOTORO_FLASH_DIR | Каталог пары; local/flash, затем старый build/sbl-stock |
| TOTORO_ONENAND_IMAGE | Явный путь основных данных, приоритет над каталогом |
| TOTORO_ONENAND_OOB | Явный путь spare-данных |
| TOTORO_ONENAND_RW | 1 — запись разрешена, 0 — запрещена |
| TOTORO_ONENAND_PROBE | Лаунчеры ставят 1, включая модель |
| TOTORO_ONENAND_TRACE | 1 — диагностика; 2 — подробный большой лог |

Обычный лаунчер разрешает запись по умолчанию при выборе пары из каталога.
Если main задан явно, запись по умолчанию запрещена. Консоль по умолчанию
всегда запрещает запись. Подготовщик разрешает её только для создаваемой пары.
При явном выборе файлов лучше задавать сразу main, OOB и режим записи.

Экспериментальные `TOTORO_FAST_DELAY`, `TOTORO_IPC_PROBE`,
`TOTORO_MODEM_TRANSPORT`, `TOTORO_WIFI_PROBE`, `TOTORO_V3D_SYNC`,
`TOTORO_V3D_DEBUG` для описанного запуска не требуются.
Их наличие не означает полной поддержки этих подсистем.

| Объект | Адрес |
| --- | --- |
| SDRAM | 0x80000000, 512 MiB |
| SBL | 0x96800000 |
| OneNAND MMIO | 0x00400000 |
| UART | 0x08820000 |
| LCDC | 0x08030000 |
| Используемый framebuffer Linux | 0x93500000 |

CPU по умолчанию — QEMU `arm1136`. Адреса и регистры сверяйте с исходниками
этого дерева: модель не является полной спецификацией BCM21553.

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| Missing file | Собраны ли QEMU, доступны ли SBL и оба файла флеша |
| Unsupported SBL hash | Для консоли/подготовки нужна первая версия SBL из таблицы |
| Output already exists | Укажите новый каталог, старый намеренно не форматируется |
| Нет машины totoro | Запускается системный QEMU или другой target |
| Ошибка GTK | Наличие GTK в сборке и графической сессии |
| Чёрный экран | Не указан ли display none; не сменился ли уже логотип |
| BML 0x90040000, PC около 0x9680d380 | Пустой/несогласованный флеш или нет BML-метаданных |
| Ошибка J4FS, нет логотипа | param.lfs должен пройти STL-подготовку |
| Linux вошёл, Android не появился | Полная загрузка Android пока не подтверждена |
| Огромные логи | Уберите подробный TRACE и трассировку инструкций |

```sh
mkdir -p local/logs
TOTORO_ONENAND_TRACE=1 TOTORO_ONENAND_RW=0 \
sh scripts/run-totoro-sbl.sh -display gtk,gl=off \
    2>local/logs/onenand.log
```

В QEMU monitor полезны `info registers` и `screendump local/logs/screen.ppm`.
Каталог снимка должен существовать. Снимок фиксирует только текущий экран.

## Публикация на GitHub

Публикуются исходники QEMU с изменениями платы, документация и три рабочих
скрипта totoro. Сборки, прошивки, локальные образы и временные тесты исключены
через `.gitignore`. Не применяется глобальное исключение всех `*.bin` / `*.img`:
в исходном QEMU есть необходимые двоичные данные и fixtures.

```sh
git status --short
git diff --stat
git diff --check
git ls-files --others --exclude-standard
git check-ignore build/ build-win/ local/ .local-artifacts/
```

Проверьте состав добавляемых файлов и существующие изменения, включая
изменения типов файлов и символических ссылок. Очистка скриптов не
восстанавливает и не переписывает исходники автоматически.
`.gitignore` не удаляет ранее закоммиченные файлы из индекса или истории.
Не добавляйте прошивки принудительно через `git add -f`.

Копирование всей папки в ZIP **не учитывает** `.gitignore`.
Публикуйте проверенный набор Git-файлов; локальные архивы и сборки остаются на диске.
